# О чём talk'уют деньги — автопостинг новостей

Раз в час пайплайн берёт свежие заголовки с CNBC, NYT, BBC (RSS) и Bloomberg
(их официальный телеграм-канал), переводит на русский и добавляет короткий
авторский комментарий через Claude API, публикует в канал через Telegram Bot
API. Хостинг — GitHub Actions (бесплатно).

## Разовая настройка

### 1. Секреты репозитория

В **GitHub, в этом репозитории** → вкладка **Settings** → в левом меню
**Secrets and variables** → **Actions** → кнопка **New repository secret**.
Добавить три секрета:

| Имя | Что туда | Где взять |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | токен бота-администратора канала | у @BotFather в Telegram, `/mybots` → выбрать бота → API Token |
| `TELEGRAM_CHAT_ID` | `@talkuyut_dengi` (или числовой id канала, если username недоступен боту) | обычно достаточно username канала с `@` |
| `ANTHROPIC_API_KEY` | ключ Anthropic API | [console.anthropic.com](https://console.anthropic.com/) → Settings → API Keys → Create Key |
| `TELEGRAM_ADMIN_CHAT_ID` | твой личный числовой id в Telegram (не канал) — сюда бот пришлёт сообщение, если пайплайн упадёт с ошибкой | см. раздел «Уведомления о сбоях» ниже |

### 2. Права записи для Actions

Там же, в **GitHub** → **Settings** этого репозитория → в левом меню
**Actions** → **General** → раздел **Workflow permissions** внизу страницы →
выбрать **Read and write permissions** → **Save**.

Это нужно, чтобы workflow мог коммитить обновлённый `state/posted.json`
(список уже опубликованного) обратно в репозиторий после каждого запуска.

### 3. Первый запуск

Первый запуск **ничего не публикует** — он только запоминает все заголовки,
которые видит прямо сейчас в фидах (`bootstrapped: false → true` в
`state/posted.json`). Это специально, чтобы в канал не улетела разом вся
история фидов. Со второго запуска в канал будут уходить только новые
заголовки.

Запустить вручную можно в **GitHub** → вкладка **Actions** → workflow
**«Публикация новостей»** в списке слева → кнопка **Run workflow** справа.
По расписанию (раз в час) он и так будет запускаться сам — `cron` в
`.github/workflows/publish.yml`.

## Локальная проверка перед боевым запуском

```bash
pip install -r requirements.txt
export TELEGRAM_BOT_TOKEN=... TELEGRAM_CHAT_ID=@talkuyut_dengi ANTHROPIC_API_KEY=...
DRY_RUN=1 python main.py   # печатает готовые посты в консоль, ничего не публикует
```

Если всё выглядит хорошо — убрать `DRY_RUN=1` и прогнать ещё раз (это будет
первый боевой запуск — bootstrap, без публикаций, см. выше), либо просто
дать сработать первому запуску в Actions.

## Добавить/убрать источник

Список источников — в `src/config.py`, список `SOURCES`. Для RSS достаточно
имени и ссылки на фид. Для телеграм-канала (как Bloomberg) — имя канала без
`@`, работает через публичную веб-версию `t.me/s/<канал>`, авторизация не
нужна.

## Уведомления о сбоях

Если запуск пайплайна падает с ошибкой (например, снова истёк/сломался
API-ключ, отозван токен бота, недоступен источник), бот пришлёт тебе личное
сообщение в Telegram — не в канал, а лично тебе. Чтобы это включить:

1. Открой личный чат со своим ботом в Telegram (тем же, чей токен в
   `TELEGRAM_BOT_TOKEN`) и отправь ему любое сообщение, например `/start`.
   Это обязательный шаг — бот не может написать первым тому, кто ни разу не
   писал ему.
2. В браузере открой:
   `https://api.telegram.org/bot<ТВОЙ_ТОКЕН_БОТА>/getUpdates`
   (вставь свой реальный токен вместо `<ТВОЙ_ТОКЕН_БОТА>`).
3. В открывшемся JSON найди `"chat":{"id":ЧИСЛО, ...}` — это число и есть
   твой личный `TELEGRAM_ADMIN_CHAT_ID`. Обычно это отрицательное число для
   групп и положительное для личных чатов — у тебя должно быть положительное.
4. Добавь его как секрет репозитория `TELEGRAM_ADMIN_CHAT_ID` (см. раздел
   «Секреты репозитория» выше).

Если секрет не задать — пайплайн продолжит работать как обычно, просто
уведомлений о сбоях не будет (шаг уведомления в этом случае тихо ничего не
отправит).

## v2 — минимальный запуск (аналитический выпуск, без кнопок)

26.09.2026, вечер — решение менеджера проекта: запускаем v2 в минимальной
конфигурации (без кнопок «Опубликовать»/«Отклонить» и без обработчика через
Cloudflare Worker — это вторая неделя). Выпуск дважды в день (08:00/19:00
МСК) уходит АВТОРУ В ЛИЧКУ, автор публикует в канал сам — пересылкой из
личных сообщений со включённым «Скрыть имя отправителя» (в Telegram:
удержать сообщение → Переслать → переключатель имени отправителя). v1
продолжает работать параллельно до момента явного переключения (см. ниже).

### Новые секреты репозитория

Кроме уже описанных выше (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`,
`ANTHROPIC_API_KEY`, `TELEGRAM_ADMIN_CHAT_ID`) — добавить:

| Имя | Что туда | Где взять |
|---|---|---|
| `TELEGRAM_AUTHOR_CHAT_ID` | твой личный числовой id — сюда v2 присылает готовый выпуск на проверку/публикацию | так же, как `TELEGRAM_ADMIN_CHAT_ID` выше (шаги 1-3) — можно поставить то же самое число, если это один и тот же человек; это ДВА разных секрета в GitHub (один про технические сбои, другой про сам редакционный контент), даже если значение совпадает |

Плюс одна переменная (не секрет — не чувствительное значение): **GitHub** →
**Settings** этого репозитория → **Secrets and variables** → **Actions** →
вкладка **Variables** → **New repository variable**:

| Имя | Значение | Когда ставить |
|---|---|---|
| `V1_DISABLED` | `1` | В МОМЕНТ переключения на v2 — см. «Отключение v1» ниже. Пока не задана (или любое другое значение) — v1 работает как обычно. |

Модель/effort Аналитика и Фактчекера после результата воскресного A/B —
тоже переменные (Variables, не секреты): `V2_MODEL_ANALYST`,
`V2_ANALYST_EFFORT`, `V2_MODEL_FACTCHECKER`, `V2_FACTCHECKER_EFFORT` (см.
`src/config.py` — пока не заданы, действует дефолт: Sonnet 5, effort=medium
у обоих).

### Настройка Cloudflare Worker для v2

Новый workflow `.github/workflows/publish_v2.yml` принимает
`workflow_dispatch` с полями `mode` (`collect` или `issue`) и, опционально,
`hours` (только для `mode=issue`). Готовый код Worker'а — целиком, для
вставки в дашборд — лежит в `cloudflare/worker.js` этого репозитория (сам
Worker при этом настраивается ВНЕ репозитория, руками, в дашборде
Cloudflare — код здесь только как готовый к копированию файл и как
версионируемая копия на будущее).

**Это ОТДЕЛЬНЫЙ, НОВЫЙ Worker — не правка существующего Worker'а v1.**
Исходный код Worker'а v1 (тот, что дёргает `publish.yml` каждые ~15 минут)
не виден в этом репозитории — он живёт только в дашборде Cloudflare, и
трогать его отсюда наугад рискованно. Проще и безопаснее завести под v2
второй, полностью отдельный Worker.

**Шаг 1 — создать Worker.** Дашборд Cloudflare (dash.cloudflare.com) →
слева **Workers & Pages** → кнопка **Create** → карточка **"Start with
Hello World!"** → **Get started** → задать имя (например
`talkuyut-dengi-v2`) → **Deploy** → **Continue to project**.

**Шаг 2 — вставить код.** На странице Worker'а — кнопка **Edit code**
(открывает редактор в браузере) → выделить весь код-заглушку и заменить
на содержимое `cloudflare/worker.js` из этого репозитория целиком → кнопка
**Deploy** (без неё изменения не сохранятся).

**Шаг 3 — секрет с токеном GitHub.** На странице Worker'а → вкладка
**Settings** → раздел **Variables and Secrets** → **Add** → имя
`GITHUB_TOKEN`, **Type** переключить на **Secret** (это и делает значение
скрытым — обычный "Text" хранится открытым текстом) → вставить значение
PAT (как его получить — см. ниже) → **Deploy**.

Если такого PAT ещё нет: GitHub → аватар в углу → **Settings** →
**Developer settings** → **Fine-grained personal access tokens** →
**Generate new token** → **Repository access: Only select repositories**
→ выбрать `Habibui/Talking-money` → **Permissions** → **Actions: Read and
write** → **Generate token** → скопировать значение (показывается один
раз). Если у тебя уже есть такой PAT для Worker'а v1 с этим же правом на
этот же репозиторий — можно использовать то же значение, но секрет всё
равно нужно завести отдельно именно в ЭТОМ Worker'е (Cloudflare не делится
секретами между Worker'ами).

**Шаг 4 — cron-триггеры.** На странице Worker'а → **Settings** →
**Triggers** → раздел **Cron Triggers** → **Add Cron Trigger** — добавить
все три (Cron Triggers у Cloudflare — всегда UTC, часовых поясов не
понимают; МСК = UTC+3 круглый год, без перехода на летнее время):

| Cron-строка (UTC) | Что запускает | В МСК |
|---|---|---|
| `0 * * * *` | `mode=collect` | каждый час, в :00 |
| `5 5 * * *` | `mode=issue` | 08:05 |
| `5 16 * * *` | `mode=issue` | 19:05 |

Сдвиг issue-триггеров на 5 минут от часового collect — запас на всякий
случай (Worker может слегка задержаться), не жёсткое требование: с
26.09.2026 `scripts/issue_v2.py` сам первым шагом гоняет Сборщик перед
формированием выпуска (см. комментарий в самом файле), поэтому корректность
выпуска не зависит от того, успел ли отработать соседний почасовой
collect-запуск.

**Проверить без ожидания cron.** `cloudflare/worker.js` умеет и ручной
запуск — открой в браузере URL Worker'а (вида
`https://talkuyut-dengi-v2.<твой-поддомен>.workers.dev`, показывается на
странице Worker'а после деплоя) с `?mode=collect` или `?mode=issue` в
конце адреса — это сразу вызовет `workflow_dispatch`, не дожидаясь
никакого cron. Удобно ровно для воскресного живого прогона: не нужно
подгонять реальное время под 08:00/19:00 МСК.

### Отключение v1 — ТОЛЬКО после первого успешного выпуска v2

26.09.2026, поздний вечер — уточнение менеджера проекта по порядку
cutover: `V1_DISABLED=1` ставится **не в момент запуска v2, а только
после того, как первый РЕАЛЬНЫЙ выпуск v2 успешно пришёл автору в личку**.
До этого момента v1 продолжает работать как обычно, без изменений — канал
не должен замолкать, даже если первый прогон v2 упадёт с ошибкой. v2 сам
ничего не публикует в канал (см. выше), поэтому провальный первый запуск
v2 — это просто пропущенный выпуск в личке автора, а не сбой, заметный
подписчикам; откладывать отключение v1 до подтверждённого успеха v2 не
стоит ничего, кроме одного лишнего часа-двух параллельной работы обеих
версий.

Порядок:

1. Дождаться, что первый реальный выпуск v2 (по расписанию 08:00/19:00
   МСК или через ручной запуск Worker'а, см. выше) действительно пришёл
   личным сообщением в Telegram автору — то есть открыт и прочитан, не
   просто «workflow не упал с ошибкой» в логах GitHub Actions.
2. Только после этого — **GitHub** → **Settings** → **Secrets and
   variables** → **Actions** → **Variables** → задать `V1_DISABLED` = `1`
   (см. таблицу выше). Со следующего срабатывания `main.py` будет сразу
   выходить без публикации — это штатный пропуск, не ошибка (в логе
   запуска будет видно сообщение об этом, шаг «Уведомить о сбое» НЕ
   сработает).
3. Отдельно — в Cloudflare Worker'е v1 можно (не обязательно сразу, раз
   `V1_DISABLED` уже гарантирует отсутствие публикации) отключить или
   удалить cron-триггер, который дёргает `publish.yml` — чтобы не тратить
   вызовы Worker'а впустую. Это на стороне Cloudflare, вне этого
   репозитория.
4. Если понадобится откатиться на v1 — просто убрать/сменить значение
   `V1_DISABLED` (или снова включить cron/Worker-триггер на `publish.yml`,
   если его отключали).

## Известные ограничения

- Расписание GitHub Actions (`schedule`) — это гарантия «не раньше», а не
  «ровно в такое-то время»: в моменты высокой нагрузки на GitHub запуск может
  сдвинуться на несколько минут. На дедуп по `state/posted.json` это не
  влияет.
- `t.me/s/<канал>` — не официальный API, а публичная HTML-страница
  предпросмотра. Работает стабильно, но при существенном изменении вёрстки
  Telegram может потребоваться поправить `src/sources.py`.
- Если один и тот же инфоповод выходит у нескольких источников почти
  одновременно — пайплайн пока не дедуплицирует по смыслу, только по
  конкретной ссылке. Это можно добавить позже (например, сравнение похожести
  заголовков), если начнёт мешать.
